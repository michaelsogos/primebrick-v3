# Plan: Auth Toggle for All API Catalog Pages

## Objective

Add the "Authorize" shield icon to every API page on docs.primebrick.dev, matching the cosmocargo demo site. The shield lets users toggle between Bearer JWT and X-API-Key authentication in the REPL playground.

**Server selector feature is deferred** — will be addressed in a future plan.

---

## Empirical Investigation Results (ZERO ASSUMPTIONS)

### What cosmocargo has (verified live at https://www.cosmocargo.dev/api-shipments/shipment-management)

- **Auth toggle**: Shows "Bearer (JWT) or X-API-Key (header)" — comes from TWO security schemes in the OpenAPI spec:
  ```json
  "security": [{ "BearerAuth": [] }, { "ApiKeyAuth": [] }],
  "components": {
    "securitySchemes": {
      "ApiKeyAuth": { "type": "apiKey", "in": "header", "name": "X-API-Key" },
      "BearerAuth": { "type": "http", "scheme": "bearer", "bearerFormat": "JWT" }
    }
  }
  ```

### What Primebrick specs currently have (verified by reading source)

#### BE — `D:/git/primebrick/primebrick-be-v3/src/openapi/openapi.ts`
- `servers`: Only ONE server: `http://localhost:3001` ("Local development server")
- `securitySchemes`: Only `bearerAuth` (type: http, scheme: bearer, bearerFormat: JWT)
- `security` at operation level: `[{ bearerAuth: [] }]` on protected endpoints
- NO `apiKey` security scheme defined

#### US (EmailSender) — `D:/git/primebrick/primebrick-us-v3/emailsender/src/server/openapi-route.ts`
- `servers`: NOT defined at all (no `servers` key in the spec)
- `securitySchemes`: NOT defined at all
- The webhook endpoint mentions "API key auth" in its tag description but has no formal security scheme

#### Docs — `D:/git/primebrick/primebrick-v3-docs/zudoku.config.tsx`
- `generated-apis.ts` (auto-generated by `fetch-openapi.mjs`): Each API has `disableSecurity: false` — security display is already enabled
- `defaults.apis`: NOT configured (no global defaults)

### How Zudoku auth shield toggle works (verified from Zudoku docs + source)

When `disableSecurity: false` (already set) AND the spec has `securitySchemes` defined, Zudoku shows:
- Security badges on operations ("Bearer (JWT)" etc.)
- An "Authorize" shield icon in the playground that opens a dialog where users enter credentials
- If multiple security schemes exist (e.g., Bearer + API Key), users can choose which to use

| Feature | What's needed | Where |
|---------|--------------|-------|

## Detailed Implementation Plan

### Phase 1: Add API Key security scheme to BE OpenAPI spec

**File**: `D:/git/primebrick/primebrick-be-v3/src/openapi/openapi.ts`

**Change 1 — Add apiKey security scheme** (inside `securitySchemes`, after `bearerAuth`):
```typescript
securitySchemes: {
  bearerAuth: {
    type: "http",
    scheme: "bearer",
    bearerFormat: "JWT",
    description: "OAuth 2.1 Bearer token obtained via the Authorization Code flow. See /.well-known/oauth-authorization-server for discovery endpoints.",
  },
  apiKey: {
    type: "apiKey",
    in: "header",
    name: "X-API-Key",
    description: "API key passed via the X-API-Key header. Used for service-to-service authentication and MCP client access.",
  },
},
```

**Change 2 — Add top-level `security` array** (after `servers`, before `tags`):
```typescript
security: [{ bearerAuth: [] }, { apiKey: [] }],
```

This makes both auth methods available on ALL endpoints by default. Individual endpoints that already have `security: [{ bearerAuth: [] }]` will override this and only show Bearer. If we want BOTH on every endpoint, we need to update each operation's security to `[{ bearerAuth: [] }, { apiKey: [] }]`.

**Decision needed from user**: Should ALL endpoints show both Bearer + API Key, or only specific ones?

### Phase 2: Add security schemes to US (EmailSender) OpenAPI spec

**File**: `D:/git/primebrick/primebrick-us-v3/emailsender/src/server/openapi-route.ts`

**Change 1 — Add `security` and `securitySchemes`** (add at top level + in `components`):
```typescript
security: [{ bearerAuth: [] }, { apiKey: [] }],
components: {
  securitySchemes: {
    bearerAuth: {
      type: "http",
      scheme: "bearer",
      bearerFormat: "JWT",
      description: "OAuth 2.1 Bearer token from the Primebrick backend.",
    },
    apiKey: {
      type: "apiKey",
      in: "header",
      name: "X-API-Key",
      description: "API key for service-to-service authentication.",
    },
  },
},
```

**Note**: The webhook endpoint (`/api/v1/webhook/:provider`) uses API key auth specifically. Its operation-level security should be `[{ apiKey: [] }]` only.

### Phase 3: Verify fetch-openapi.mjs preserves securitySchemes

**No changes needed** — the script already passes through `securitySchemes` and `security`.

## Deferred: Server Selector

The server selector feature (custom server URL + localStorage persistence) is deferred to a future plan. Key findings from the investigation are preserved here for reference:

- Zudoku's `Endpoint.tsx` hides the server dropdown when only 1 server exists (`if (servers.length <= 1) return null`)
- Zudoku already persists selected server in localStorage (key `zudoku-selected-server`) via Zustand `persist` middleware
- No plugin hook or slot exists to inject custom server UI
- The specs are static (build-time from GitHub repos), so adding fake URLs has no value
- A custom plugin (DOM injection or Vite alias override) would be needed to let users add their own server URL at runtime
